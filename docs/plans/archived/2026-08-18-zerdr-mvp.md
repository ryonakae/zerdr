## Problem Statement

Zed and Herdr can each keep several project workspaces, but changing the focused Herdr workspace does not focus the corresponding project inside the current Zed OS window. The current public APIs do not expose Zed workspace-change events to extensions, and Herdr plugin events do not identify the outer terminal client that caused an event. zerdr must provide reliable synchronization without modifying Herdr or Zed, opening a new Zed window, or replacing the current Zed multi-workspace.

## Goal

Deliver a Rust CLI, Herdr plugin integration, and Zed tasks that keep a dedicated Herdr session and one Zed OS window aligned while `zerdr herdr` is running inside a Zed integrated terminal. The MVP must:

- synchronize normal Herdr workspace focus changes to Zed automatically;
- offer Zed task commands for fuzzy picking, next, previous, and explicit resynchronization;
- identify workspaces by canonical local Git checkout roots;
- preserve Herdr session state while limiting synchronization to live Zed-launched clients;
- install, diagnose, uninstall, test, and distribute the integration on macOS and Linux.

## Out of Scope

- Modifying Herdr or Zed core.
- A Zed extension.
- Detecting Zed's standard sidebar or workspace changes and automatically driving Herdr.
- More than one Zed OS window.
- Using the dedicated `zerdr` Herdr session from Ghostty or another external terminal.
- Remote, SSH, WSL, or container workspaces.
- Non-Git workspaces.
- Zed multi-root projects, monorepo subproject roots, or a Zed project rooted below the Git checkout root.
- Selecting an OS window when several Zed windows are open.
- crates.io publication in the MVP.
- Automated real-Zed GUI E2E in CI.
- Homebrew `post_install` changes to user configuration.

## Requirements and Decisions

### Requirements

- **R1 — Zed-scoped lifecycle:** `zerdr herdr` must require both `ZED_TERM=true` and `TERM_PROGRAM=zed`, launch or attach the named persistent Herdr session `zerdr`, and keep synchronization enabled only while at least one such wrapper client is alive.
- **R2 — Persistent Herdr session:** Exiting the wrapper must release only that client's live lease. It must not stop or delete the `zerdr` Herdr session. Multiple Zed-launched wrapper clients are allowed.
- **R3 — Automatic Herdr-to-Zed synchronization:** The Herdr plugin must subscribe to `workspace.focused`. For the `zerdr` session, and only while a matching live lease exists, it must resolve the focused workspace binding and invoke `zed --existing <canonical-checkout-root>`.
- **R4 — Startup synchronization:** After a wrapper has attached and established its lease, zerdr must synchronize Zed to the currently focused Herdr workspace even if attaching did not emit `workspace.focused`.
- **R5 — Existing Zed window semantics:** Synchronization must use `--existing`, never `--new` or `--reuse`. With the MVP's one-window precondition, an existing matching project is activated and an absent checkout is added to that same window.
- **R6 — Manual switching commands:** `pick`, `next`, `previous`, and `sync` must require the Zed terminal environment and a live lease. `pick` uses an embedded fuzzy picker. `next` and `previous` follow Herdr's returned display order and wrap at both ends.
- **R7 — Single synchronization path:** For a change to a different Herdr workspace initiated by `pick`, `next`, or `previous`, the command validates the target and calls `herdr workspace focus`; the plugin event performs the normal Zed switch. Selecting the already-focused workspace and `sync` call the same sync use case directly because Herdr may not re-emit `workspace.focused`.
- **R8 — Stable path identity:** A Herdr workspace maps to exactly one canonical local Git checkout root. Resolution prefers Herdr `worktree.checkout_path`; otherwise it resolves the selected workspace's focused-pane/workspace CWD with `git rev-parse --show-toplevel`. The first valid root is persisted and does not change when a pane later changes CWD.
- **R9 — Explicit binding management:** `bind [PATH]` resolves the supplied path, or the command CWD when omitted, through `git rev-parse --show-toplevel`, canonicalizes that checkout root, replaces the focused workspace's binding, and immediately synchronizes Zed. `unbind` removes the focused workspace's binding. A missing persisted root is not automatically rebound; a new or unbound workspace may be lazily resolved and bound on first focus or selection.
- **R10 — Binding cardinality:** Several Herdr workspace IDs may map to the same checkout. Picker and next/previous retain each Herdr workspace as a separate item.
- **R11 — Preflight and failure behavior:** Manual switching validates or lazily resolves the target root before changing Herdr. If that preflight fails, neither side changes. If `zed --existing` fails after Herdr has changed, Herdr is not rolled back; zerdr emits a Herdr notification on every eligible synchronization failure—including a corrupt locked lease in the matching socket scope—and `sync` is the recovery path. Unlocked stale leases remain a successful no-op and cleanup case.
- **R12 — Picker and task UX:** The picker task opens in the center, hides on success or cancellation, and stays visible on a command error. Because Zed 1.15 has no failure-only reveal mode, next, previous, and sync use `reveal: no_focus` plus `hide: on_success`: their terminal is visible without focus while running, then closes on success or when a failure is delivered through Herdr notification. If no live lease/notification target exists, the task terminal remains visible with actionable `zerdr herdr` guidance.
- **R13 — Setup lifecycle:** `setup` idempotently installs/links the Herdr plugin and merges four owned global Zed tasks without editing keybindings. It prints keybinding examples. `uninstall` removes only zerdr-owned plugin/task entries and preserves bindings; `uninstall --purge` also removes zerdr state. `doctor` reports actionable compatibility, installation, session, lease, binding, executable, and task problems.
- **R14 — Compatibility:** Herdr 0.8.0 / protocol 19 and Zed 1.15.0 are the initial verified baseline. `doctor` must inspect required capabilities, including Herdr plugin/event support and Zed `--existing`, instead of relying only on version comparisons.
- **R15 — Platform and distribution:** Runtime behavior supports macOS and Linux. Release artifacts cover `aarch64-apple-darwin`, `x86_64-apple-darwin`, `aarch64-unknown-linux-gnu`, and `x86_64-unknown-linux-gnu`. GitHub Releases and `ryonakae/homebrew-tap` are published through `dist`; installation does not run setup automatically.
- **R16 — Quality:** Development follows Red-Green-Refactor. CI runs formatting, Clippy, unit tests, and fake-process integration tests. Real Zed/Herdr behavior is release-gated by a documented manual macOS E2E checklist.
- **R17 — Repository presentation:** The public repository has an English README, MIT license, one fast Homebrew install path, concise setup and usage examples, compatibility boundaries, and troubleshooting commands.

### Implementation Decisions

- **D1 — Rust binary:** Use one Rust binary so process control, JSON contracts, fuzzy selection, file locking, and cross-platform releases do not require a shell or Node runtime.
- **D2 — Adapter seams:** Keep orchestration separate from Herdr CLI, Zed CLI, process environment, filesystem/state, notification, and picker adapters. Tests substitute fake executables and temporary state roots rather than depending on running GUIs.
- **D3 — Fixed session:** The only managed Herdr session name is `zerdr`. `herdr --session zerdr <command>` targets it. Supporting arbitrary session names would reintroduce session/window routing into the MVP.
- **D4 — Lease set:** Store one lease per wrapper client and hold an OS file lock for the wrapper lifetime. A plugin event is eligible when at least one valid locked lease has a canonical socket path equal to `HERDR_SOCKET_PATH`. Released or crashed-client files are stale and may be removed after their locks can be acquired. A locked lease in the event socket's lease directory that cannot be decoded or canonicalized is a synchronization failure, not evidence that no lease exists.
- **D5 — Global plugin guard:** The plugin is installed globally because Herdr Plugin v1 is global. Its event command must no-op successfully for every socket that has no matching live zerdr lease.
- **D6 — Canonical roots:** Discovery and explicit `bind` candidates are first resolved to their Git top-level and then canonicalized before persistence or comparison. The persisted value must be that canonical top-level; linked worktrees therefore use the checkout path rather than the main repository root.
- **D7 — Event concurrency:** Sync commands serialize by session/socket so concurrent `workspace.focused` hooks cannot reorder Zed activations. After acquiring the lock, the handler re-reads the focused workspace and binding before invoking Zed.
- **D8 — No manual-switch suppression token:** Different-workspace task commands do not invoke Zed directly, so they do not create the duplicate plugin/CLI call that would require suppression state.
- **D9 — Embedded assets:** The binary carries the Herdr manifest and Zed task templates. `setup` materializes a versioned plugin directory under zerdr's data directory and links it with Herdr. Generated commands use the stable executable path found by setup, not a versioned Homebrew Cellar path.
- **D10 — Safe config merge:** Setup preserves unrelated Zed tasks, refuses to replace conflicting non-zerdr entries with the owned labels, and writes through a temporary file plus atomic rename. Setup records a fingerprint of each generated task payload in zerdr install state. Uninstall removes an entry only when its label and current payload match the recorded zerdr-owned fingerprint; same-label foreign or user-modified entries are preserved and reported. Existing files are backed up before the first mutation in a command.
- **D11 — Standard directories with test override:** Resolve config, data, and state roots through platform conventions, honoring XDG variables where applicable and an internal test override. `doctor` prints the resolved locations. Exact platform paths are encapsulated rather than spread through commands.
- **D12 — Release automation:** Use `dist` to build archives, checksums, GitHub Releases, and the Formula update in the existing public `ryonakae/homebrew-tap` repository. Release tags follow SemVer with a `v` prefix.

### Contracts

#### Public CLI

```text
zerdr herdr
zerdr pick
zerdr next
zerdr previous
zerdr sync
zerdr bind [PATH]
zerdr unbind
zerdr setup
zerdr uninstall [--purge]
zerdr doctor
```

An internal, hidden event entry point is reserved for the Herdr manifest:

```text
zerdr sync-from-herdr
```

Command rules:

- `herdr`, `pick`, `next`, `previous`, `sync`, `bind`, and `unbind` operate only on the fixed `zerdr` session.
- User-facing synchronization commands require the Zed environment and a matching live lease, except that `herdr` creates its lease after the child session socket becomes available.
- `setup`, `uninstall`, and `doctor` may run outside Zed.
- `sync-from-herdr` authenticates its invocation using `HERDR_PLUGIN_CONTEXT_JSON`, `HERDR_PLUGIN_EVENT`, and `HERDR_SOCKET_PATH`; it does not trust ambient `TERM_PROGRAM` because plugin processes inherit the Herdr server environment.
- Generated next/previous/sync tasks set a private task-delivery marker. If an operation failure is successfully delivered through Herdr notification, task mode exits successfully so hide-on-success removes the task terminal. If notification delivery is unavailable, task mode writes `zerdr herdr` guidance and exits nonzero so the terminal remains. Direct CLI invocations do not mask operation failures.
- Cancellation from `pick` exits successfully without changing either side. Invalid usage and other actionable command failures exit nonzero.

#### Binding state

The persisted contract is versioned and keyed by the stable Herdr workspace ID:

```json
{
  "schema_version": 1,
  "session_name": "zerdr",
  "bindings": {
    "w1": "/canonical/path/to/checkout"
  }
}
```

Invariants:

- every value is an absolute canonical Git top-level when written; explicit nested paths and an omitted-path CWD are both normalized to that top-level;
- duplicate values are allowed;
- an existing binding is never silently changed by CWD discovery;
- unsupported schema versions fail with an actionable error rather than being overwritten;
- writes use temporary files and atomic rename.

#### Live lease

Each wrapper owns a separate versioned lease record under a socket-derived directory:

```json
{
  "schema_version": 1,
  "session_name": "zerdr",
  "socket_path": "/canonical/path/to/herdr.sock",
  "wrapper_pid": 123,
  "client_pid": 124,
  "created_unix_ms": 1787000000000
}
```

The record alone is not proof of liveness. The wrapper-held OS lock is authoritative. Matching requires the canonical lease socket path to equal the event's canonical `HERDR_SOCKET_PATH`. An unlocked record is stale. A locked but unreadable/invalid record inside the event socket's lease scope is an eligible synchronization failure and must notify rather than silently no-op.

#### Owned Zed tasks

Setup owns exactly these labels:

```text
zerdr: Pick Workspace
zerdr: Next Workspace
zerdr: Previous Workspace
zerdr: Sync Workspace
```

The picker task uses a centered reveal target, hides on success/cancellation, and remains visible on command failure. Next, previous, and sync use `reveal: no_focus`, `hide: on_success`, and a task-delivery mode: the non-focused terminal closes when successful or when Herdr notification delivery succeeds, but remains with `zerdr herdr` guidance when no notification target is available. Direct CLI invocation still writes failures to stderr. Setup records each generated task payload fingerprint; task ownership requires both an owned label and a matching fingerprint. Keymap entries are examples only and remain user-owned.

#### Sync state transitions

```text
Herdr standard focus
  -> workspace.focused plugin event
  -> matching live socket lease?
     no: successful no-op
     yes: serialize, re-read focused workspace, resolve binding
          -> zed --existing ROOT
          -> success, or Herdr notification + nonzero event result

Zed pick/next/previous to a different workspace
  -> require Zed environment + live lease
  -> resolve and validate target binding
  -> herdr workspace focus ID
  -> plugin event owns the Zed switch

Zed pick of current workspace / zerdr sync
  -> require Zed environment + live lease
  -> run shared sync use case directly
```

## Testing Decisions

- **Test seam:** Run the compiled CLI against fake `herdr`, `zed`, and `git` executables placed first in `PATH`, with isolated platform directories and deterministic JSON responses. Use real temporary Git repositories only for canonical-root and linked-worktree behavior.
- **Behavior:** Assert observable command order, arguments, state files, locks, exit status, stdout/stderr, notifications, and preservation of unrelated config. Do not assert private helper call graphs.
- **Concurrency:** Hold/release real file locks from child processes to prove multiple-client lease semantics, stale cleanup, socket isolation, and serialized event handling.
- **Configuration:** Exercise absent, valid, commented/JSONC-compatible, conflicting, and malformed Zed task files. A failed merge must leave the original byte-for-byte unchanged.
- **Prior art:** There is no repository-local prior art because the repository is empty. Follow standard Rust integration-test boundaries and the documented Herdr/Zed CLI JSON contracts.
- **Avoid:** Do not launch a real Zed GUI in automated tests, depend on the user's actual Herdr session/config, compare display snapshots of the picker, or encode private module layouts into tests.

## Risks and Open Questions

### Risks

- Zed 1.15.0 `--existing` behavior is confirmed from CLI/source but still needs the planned real one-window E2E check.
- Herdr plugin hooks are asynchronous; a Zed failure after Herdr focus can temporarily desynchronize the applications by design. Notifications and `sync` are the agreed recovery mechanism.
- Herdr's global plugin scope requires exact socket/lease guarding. A bug in canonical socket matching could affect unrelated sessions, so no-op isolation tests are release-blocking.
- File-lock semantics and atomic rename behavior differ at filesystem boundaries. State and integration files must stay on the same filesystem as their temporary replacements.
- Zed global task files may contain JSONC and user formatting. Setup must fail safely rather than rewrite syntax it cannot preserve.
- The Homebrew publish job requires a narrowly scoped secret with write access to the existing tap; release planning can be completed before that credential is configured.
- Directly attaching Ghostty to `herdr --session zerdr` while a Zed lease is live cannot be distinguished through Herdr's public API and is explicitly unsupported.

### Open Questions

None. Changes to public behavior, schemas, session scope, platform scope, or distribution require user confirmation and a plan update before implementation.
